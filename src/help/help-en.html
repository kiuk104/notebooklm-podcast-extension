NotebookLM Podcast Sync — Help

A Chrome extension that pushes NotebookLM Audio Overviews to your own GitHub repository and turns them into a personal podcast RSS feed.

1. How it works

NotebookLM notebook page (audio overview cards)
  → Extension [Download] button
    → Chrome downloads the audio (also saved to your local folder)
    → In parallel, the extension service worker re-fetches the same audio
      → PUTs it to docs/episodes/ via the GitHub Contents API
        → (Repo's GitHub Actions workflow) rebuilds feed.xml
          → Podcast app → new episode

After the one-time setup, every new audio overview just needs one click on [Download] in the extension.

2. First-time setup

2-1. Create an empty public GitHub repo

  1. Create a new repository on GitHub. Public (the RSS must be reachable from podcast apps).
  2. Open Settings → Pages and set Source to main branch / /docs folder.
  3. After activation, note the Pages URL: https://<user>.github.io/<repo>/
  4. The final RSS URL will be: https://<user>.github.io/<repo>/feed.xml — subscribe to this in your podcast app.

2-2. Create a Personal Access Token (PAT)

  1. Open the new PAT page (the required scope is preselected).
  2. Set Note to something identifiable (e.g., notebooklm-podcast-extension) and choose an expiration.
  3. Only the repo scope is needed.
  4. Click [Generate token] → copy the displayed ghp_... token (you cannot view it again).
The token is shown only once. Paste it into the extension options before closing the page. If you lose it, you have to issue a new one.

2-3. Enter your settings on the admin page

  1. Click the extension icon → ⚙ Admin at the bottom of the popup.
  2. Paste the PAT into the Token field.
  3. Enter Repo in owner/name form (e.g., kiuk104/my-notebooklm-podcast).
  4. RSS feed mode: keep the default Delegate to GitHub Actions (see §4).
  5. Leave the committer name/email blank to use GitHub's defaults.
  6. Click [Save], then [Verify] to confirm the token + repo actually work. ✓ <user> → <repo> push OK. All set. means good.
[Verify] calls GET /user + GET /repos/<owner>/<name> to validate the token itself + repo access/push permission in one step. It catches 401 / 404 / no-push-permission before any download flow.

3. Usage

Three modes — from a single light card to a full sweep of every notebook.

3-1. Single card (one at a time)

  1. Open a NotebookLM notebook page that has an audio overview (https://notebooklm.google.com/notebook/<id>).
  2. Press F5 once on that page so the content script gets injected (needed right after install or extension reload).
  3. Click the extension icon in the toolbar → [Scan current notebook].
  4. The notebook title / creation date + audio overview list appears.
  5. Click [Download] next to the card you want.
  6. Status flows through: downloading → ⬇ downloaded, pushing → ✓ push OK.

3-2. Bulk download from current notebook (checkboxes)

The same [Scan current notebook] result has a checkbox next to each card.

  • Cards already pushed to the repo (matched by artifact UUID) are unchecked by default and labeled ↻ already pushed.
  • Placeholder-titled cards have a disabled checkbox (re-enabled once the title resolves on a later scan).
  • The rest are checked by default — leave them as is to grab only new cards.
  • Use the top [Select all] toggle + [Download selected (N)] to bulk-download.
  • The N cards are processed sequentially — after each card's push completes, the next one starts (NotebookLM's ⋮ → Download menu only allows one open at a time, so this avoids races).

3-3. Cross-notebook sweep (v1 cron equivalent)

From any NotebookLM page, click [Scan all notebooks] in the popup. The extension runs in two stages:

Scan stage (uses background tabs in the main window):

  1. Opens NotebookLM home (/) and collects all notebook URLs.
  2. Opens each notebook page in turn and collects audio overview cards (5–10s per notebook).
  3. Closes the tab and moves on. 200 notebooks ≈ 10–15 minutes.
  4. The grouped card list appears in the popup. The result is cached for 30 minutes — you can close the popup and reopen it without rescanning.
  5. Use checkboxes to pick what to download (already-pushed cards are unchecked by default) → [Download selected].

Download stage (uses a dedicated popup window):

  1. The extension opens a small popup window via chrome.windows.create({type:"popup", focused:false}) (your main window keeps focus). NotebookLM's download trigger requires both visibilityState='visible' and a real user input gesture — a background tab in active:false state will not fire downloads.
  2. Inside that popup, the extension opens each notebook tab in turn and clicks the ⋮ → "Download" menu using chrome.debugger's Input.dispatchMouseEvent — synthesizing a genuine user click at the C++ browser level so NotebookLM sees isTrusted=true.
  3. For each card: NotebookLM starts streaming the audio → the SW re-fetches the same URL → if it's m4a/mp4, the offscreen document transcodes to mp3 (64k mono) → push to GitHub.
  4. The popup window closes automatically once all cards are done.
To auto-download new cards after a scan, enable Auto-download new cards after a scan on the admin page (⚙ Admin). With this on, the extension immediately downloads cards not yet in your repo right after [Scan all notebooks] — equivalent to the v1 cron. The first run can pull dozens or hundreds at once, so the default is OFF — start by reviewing the result and using [Last scan → Pull new] manually.
A yellow "debugging" banner appears at the top of the popup window's NotebookLM tab — Chrome's standard indicator for extensions using chrome.debugger. This is normal; it goes away when the popup closes. Your main window is unaffected.
The same audio file is also saved in Chrome's default download folder (offline backup). The repo gets a copy at docs/episodes/.

3-4. Closing the popup mid-task?

3-2 (single-notebook bulk): the popup's JS drives the loop, so closing it stops new downloads. Already started downloads continue in the background SW.

3-3 (all-notebook sweep): orchestrated entirely in the background SW, so the popup closing does not interrupt it. The card list is not restored when the popup is reopened — instead, the progress monitor on the admin page (⚙ Admin) shows the live state (scan/download stage, progress, elapsed time, errors). The background persists state to chrome.storage.session, so even closing and reopening the admin page preserves the running task view.

3-5. Progress monitor (admin page)

An all-notebook sweep or a bulk download can take 5–10 minutes (or longer), and the popup alone is awkward for tracking that. The progress panel at the top of the admin page shows:

  • Current task type (Scan all notebooks / Bulk download) + status badge (Running / Done / Failed)
  • Elapsed time (auto-formatted seconds → minutes → hours)
  • Stage message (e.g., "Scanning notebook 12/30…")
  • Progress bar (done/total)
  • Stat summary (N notebooks · N cards · N ok · N failed)
  • Error list — which notebook/card failed and why (max 20, oldest at top)
  • Recent GitHub push activity log — the last 30 push results live (✓ ok / ↻ skip / ✗ fail), card title + file size + feed update + "X seconds ago". The header shows cumulative counts and total bytes (e.g., ✓ 12 · ↻ 3 · ✗ 1 · 142.7 MB).

The [Clear] button only appears when the task is idle / completed / failed — clicking it hides the panel (the next task automatically shows it again).

The panel auto-hides when there is no task, so the form takes the full screen during normal use.

3-6. Last-scan result panel + [Pull new]

Once an all-notebook sweep completes, its result is kept in chrome.storage.session for 30 minutes. The "Last scan result" panel appears below the form on the admin page:

  • Summary: N notebooks · N cards · N new + how long ago the scan ran.
  • [Pull N new] button — start the bulk download from the admin page without reopening the popup. Progress goes to the panel above.
  • [Clear] button — drop the cached result (the next sweep will replace it).

The same result also auto-restores in the popup — closing and reopening the popup shows the cached card list within the 30-minute freshness window without rescanning.

4. RSS feed generation

The audio m4a/mp3 files in your repo alone aren't enough for podcast apps to recognize them. You also need docs/feed.xml (the RSS feed). Pick one of two modes via RSS feed mode in the extension options.

4-1. Delegate to GitHub Actions (default, recommended)

If your repo has a workflow file at .github/workflows/build-feed.yml, GitHub will rebuild and commit feed.xml every time an audio is pushed. The extension only handles the audio push, which is lightweight, and the workflow logic is fully customizable.

Standard template: see the examples/feed-builder/ folder in the extension's own repo — four files (workflow, build script, podcast.json, README) you can copy verbatim. Drop them into the same paths in your RSS-hosting repo (.github/workflows/, scripts/, docs/podcast.json) → adjust the title/owner in docs/podcast.json → push. feed.xml is generated automatically when the first audio arrives (or when you run the workflow manually from the Actions tab).

The build uses only the Python standard library, so a single setup-python step is all you need on Actions. Detailed setup / troubleshooting is in the example folder's README.

4-2. Extension generates feed.xml on every push

The extension lists the episodes directory and PUTs feed.xml right after each audio push. No workflow setup, but every audio click means two GitHub PUTs (audio + feed).

This mode uses the same metadata source as 4-1 — if docs/podcast.json exists in your repo, its title/owner/image fields are used. Without it, default metadata (title = "NotebookLM Podcast", language = "ko", owner empty) is written and a warning is logged to the SW console once. For real podcast app registration, adding docs/podcast.json is recommended (use the example as a starting point).

BASE_URL is auto-derived from the extension options' owner/name as https://<owner>.github.io/<name>/. For custom domains, mode 4-1 (workflow) is a better fit.

5. Podcast metadata (title / owner / cover)

The channel-level info shown in podcast apps (title, description, owner, cover image, category) lives in docs/podcast.json in your repo. The "Podcast metadata" section on the admin page lets you edit it from a form — no need to open the repo and edit JSON.

5-1. Edit metadata

  1. Opening the admin page (⚙ Admin) with a saved Token + Repo auto-fetches the current podcast.json and fills the form.
  2. Edit title / description / owner name / email / language / category / explicit / cover image URL.
  3. Click [Save metadata] → your repo's docs/podcast.json is updated → the workflow auto-triggers and rebuilds feed.xml with the new metadata.
  4. Podcast apps pick up the new info on their next refresh (usually tens of minutes to a few hours).

5-2. Cover image upload

iTunes/Apple Podcasts standard — JPG/PNG at least 1400×1400. Some apps reject smaller images (the pink "P" placeholder you sometimes see is the rejection state).

  1. Click Choose file on the cover image row → pick a local JPG/PNG (max 5 MB).
  2. The extension PUTs it to docs/cover.{jpg|png} in your repo (Pages serves it automatically).
  3. The image URL field auto-fills with https://<owner>.github.io/<repo>/cover.{jpg|png}.
  4. You still need to click [Save metadata] so the image field in podcast.json points to that URL and feed.xml reflects it.
External image hosts (e.g., Imgur, Cloudinary) work too — as long as the host is permanent. GitHub Pages hosting (the upload flow above) is the most stable.

5-3. Fields not exposed in the form

retention (§7) and transcode (§8) aren't in the form — they're rarely-changed technical options, and editing podcast.json directly is recommended. The metadata [Save] preserves these fields without overwriting them.

6. Pushed episodes management

The "Pushed episodes" section on the admin page shows every audio overview in your repo's docs/episodes/ as a table — same structure as the v1 admin page. With Token + Repo saved, the list auto-fetches when you open the page.

6-1. Columns

  • Date: the YYYYMMDD prefix from the filename, in ISO format.
  • Notebook: notebook slug from the filename (hyphens → spaces).
  • Title: audio overview title slug (hover reveals the full filename).
  • Format: color-coded m4a / mp3 / mp4 tag — large m4a is yellow, transcoded mp3 is green for at-a-glance identification.
  • Size: bytes shown as MB.

6-2. Sort / group

  • Click any column header to toggle asc / desc. The arrow shifts from ▲▼ → ▲ / ▼.
  • [Reset sort (date ↓)] — back to the default (newest first).
  • [Group by notebook] toggle → cards from the same notebook cluster, with a header row showing 📓 notebook (N).

6-3. Edit (jump to source NotebookLM)

Each row's [Edit ↗] button opens the corresponding NotebookLM notebook in a new tab. Audio overview titles and content are edited at NotebookLM (the source of truth) — fix them there, then [Delete] the old card here, and the next sweep will re-pull it with the new title.

If [Edit ↗] is disabled (gray), there's no recent scan result to match the notebook URL. Run [Scan all notebooks] from the popup once to refresh the mapping (kept for 30 minutes).

6-4. Delete (single / bulk)

  • Each row's [Delete] — single ghDelete (confirm dialog → 1 call → ✓).
  • Left-side checkboxes + the top [Delete selected] — multi-select bulk delete. Status updates during processing (1/N → 2/N…). Partial failures show ok/fail counts.
  • The top Select all checkbox toggles every row at once.
  • The list auto-reloads after delete.
Delete only removes the file from the repo — the NotebookLM card itself stays. On the next sweep, [Download] will re-pull it (shortId dedup prevents duplicate pushes). Useful for cleaning up wrongly-pulled cards or placeholder-titled cards.

7. Retention policy (rolling window)

To keep your repo small, add a retention field to docs/podcast.json. Both RSS modes (4-1 and 4-2) honor the same policy, so switching modes leaves the cleanup behavior unchanged.

{
  "title": "...",
  ...
  "retention": {
    "maxItems": 50,
    "maxAgeDays": 365
  }
}
FieldMeaning
maxItemsKeep only the N most recent episodes. Older files are deleted at build time.
maxAgeDaysKeep only episodes within N days of today.
maxTotalMBTotal docs/episodes/ size cap (MB). Accumulated newest-first; once the cap is hit, the rest is dropped. Designed to avoid GitHub Pages' 1 GB artifact limit. With ~5 MB-per-episode 64k mono mp3s, 900 MB ≈ 180 episodes. The newest one is always kept even if it alone exceeds the cap.

If all three are set, the policy is AND (an episode must pass all of them to stay) — the strictest one wins. To use just one, leave the others off or set them to 0. Removing the retention field disables cleanup entirely (everything is kept forever).

This is independent of NotebookLM cards — only repo files are pruned. Episodes pruned by retention disappear from RSS, but if the NotebookLM card is still alive, the next [Download] re-pushes it.

8. Transcode (m4a → mp3)

NotebookLM's m4a is 256k stereo, ~22 MB per hour. Voice-heavy audio overviews are perfectly listenable at 64k mono mp3 (~5 MB) — that's roughly 4× more capacity for the same 1 GB Pages limit. On top of that, the GitHub Contents API tops out around 37 MiB and the Git Data API blob around 40 MiB — NotebookLM's 1.5–2.5 hr overviews (40–50 MB) fall in the gap where both reject. Transcode is the workaround.

Two modes that can coexist (whichever runs first leaves an mp3, and the other becomes a no-op).

8-1. Extension-side (offscreen + lamejs, automatic)

Since v0.4.11, the extension transcodes m4a/mp4 → mp3 itself before pushing. No setup needed — m4a/mp4 inputs auto-trigger it.

  • Where: the SW fetches the audio and hands the ArrayBuffer to an offscreen document → AudioContext.decodeAudioData for PCM → lamejs Mp3Encoder for 64k mono mp3 → returned to the SW → ghPut.
  • Speed: ~10s for 30 min, ~20s for 60 min. SW memory peak: 50 MB input + 5 MB output.
  • Filename: .m4a / .mp4 automatically becomes .mp3 on push.
  • Fallback on transcode failure: the original m4a is pushed as-is — only fails (rare) if the Git Data API blob limit is then exceeded.
Old m4a/mp4 files already in your repo are not retranscoded by extension-side transcode (it only runs on the push path). To clean up old m4a/mp4 to mp3, enable the workflow-side transcode in §8-2 — the next workflow trigger will batch-convert all docs/episodes/ m4a/mp4 to mp3.

8-2. Workflow-side native ffmpeg (backward compat)

Set the transcode field in docs/podcast.json to enable the workflow's transcode step — m4a/mp4 in docs/episodes/ are converted to same-name mp3s (originals deleted). ubuntu-latest's native ffmpeg (with libmp3lame) handles 1 hour of audio in 5–10 seconds. Assumes RSS mode 4-1 (delegate to Actions). Useful for cleaning up m4a pushed by pre-v0.4.11 builds — turn it on once and the next push converts everything.

{
  ...
  "transcode": {
    "enabled": true,
    "bitrate": "64k",
    "mono": true
  }
}
FieldMeaning
enabledConvert only when true. Default false.
bitrate"64k" / "96k" / "128k" etc. "64k" for voice; "96k+" if there is significant music or sound design.
monotrue downmixes via -ac 1. NotebookLM audio overviews are mono by default, so keeping stereo wastes space.
If you combine workflow-side transcode with extension-direct RSS (4-2), an m4a-version feed appears briefly: the extension publishes m4a + an RSS pointing to it, then the workflow runs (within ~30s–1min), transcodes to mp3, and rebuilds the RSS. Podcast apps that refresh during that window may grab the m4a URL. If you use transcode, prefer RSS mode 4-1 (delegate to Actions) so everything stays consistent.

Extension-internal ffmpeg.wasm mode: not implemented. The trade-offs (+25 MB package / 100–200 MB SW memory / 30s–minutes initial response) outweigh the benefit since v0.4.11's lamejs path covers the common case. Only relevant if workflow setup proves impossible for some users.

9. Filename convention

YYYYMMDD__notebook-slug__shortId__title-slug.{m4a|mp3}
SegmentMeaning
YYYYMMDDThe cover creation date of the NotebookLM notebook (the date shown in the notebook's cover area).
notebook-slugNotebook title sanitized to alphanumerics + Korean and capped at 40 chars.
shortIdFirst 8 hex chars of the card's NotebookLM artifact UUID. Stable per-card regardless of title, used as the dedup key — re-downloading the same card or renaming the notebook / card title in NotebookLM after the fact never causes a duplicate push (works even right after a PUT, since GET responses are not cached so listings are always fresh).
title-slugThe audio overview title, slugified the same way and capped at 40 chars.

The 40-char cap guards Windows MAX_PATH (260) + GitHub's 255-byte path limit. A Korean character is 3 UTF-8 bytes, so long titles can hit GitHub's limit; the cap prevents that.

Backward compat: files pushed by versions before v0.4.0 may be in 3-segment form (YYYYMMDD__notebook__title.{ext}) without a shortId. Both RSS builders (extension and GitHub Actions workflow) recognize either format, so you can leave them as-is. New pushes use the 4-segment format.

10. Troubleshooting

"Current tab is not a NotebookLM notebook page"

The extension only operates on NotebookLM notebook detail pages (/notebook/<id>). It does not scan from the home or search pages.

"No response — please refresh the page"

The NotebookLM page was open before the extension was installed/reloaded, so the content script wasn't injected. Press F5 on that page.

Push fails with 401 Bad credentials or permission errors

  1. Click [Verify] on the admin page to find the exact failure mode — token 401 / repo 404 / no push permission.
  2. Token 401: clear and re-paste the token (watch out for hidden trailing whitespace). Still failing means the PAT expired — issue a new one (§2-2).
  3. Repo 404: typo in owner/name, or a private repo your token can't see. Check the repository access setting on the fine-grained PAT.
  4. No push permission: classic PAT needs the repo scope; fine-grained PAT needs Contents: Read and write on that repo.

Same audio overview pushed twice (e.g., __audio-0.mp3, __real-title.mp3)

NotebookLM briefly shows placeholder titles like audio 0 right after creating an audio overview, then asynchronously updates them to the real title. Downloading during the placeholder window can result in two pushes for the same audio. Wait until the title resolves before downloading. See IMPLEMENTATION_NOTES.md §1.

"Chrome tabs API locked" or "Tabs cannot be edited right now"

Multiple notebooks failing in a row with the same message during an all-notebook sweep. Causes include: actual user dragging, rapid create/close churn, conflicts with other tab-management extensions, or Chrome's internal rate limit.

The extension auto-retries up to 5 times with backoff (500ms → 8s). On 5 consecutive failures, the sweep aborts with an explanation — partial results are kept and you can act on them via [Pull new]. See IMPLEMENTATION_NOTES.md §5.

Workarounds: (a) retry without touching the tab strip, (b) temporarily disable other tab-management extensions (OneTab, tab grouping, etc.), (c) wait a moment and retry.

Download succeeded but nothing in GitHub

Check the SW devtools console:

  1. From chrome://extensions/, click the service worker link on the extension card.
  2. You should see [push] ... log lines covering the fetch / push stages.
  3. Error messages (host, status) tell you which downstream host or permission is the issue.

Bulk download "push response timeout" on every card

A bulk download started right after a sweep, every card timing out — the SW console has no [push] SW fetch host=... log at all. This signals NotebookLM rejected the download trigger from a background tab — the popup window may not have opened, or the chrome.debugger attach failed. From chrome://extensions/, check that the extension's permissions (debugger / offscreen) are granted, then reload the extension. Mechanism details: IMPLEMENTATION_NOTES.md §9, §10.

One card fails with "this file is XX MB, exceeds the GitHub blob API limit (~40 MB)"

NotebookLM's 1.5–2.5 hour overviews produce m4a files in the gap between the Contents API (~37 MiB) and Git Data API blob (~40 MiB) limits. v0.4.11+ client-side transcode normally avoids this by converting to 64k mono mp3, but if that transcode itself fails, you see this error. Rare, but if it happens:

  1. Check whether transcode itself broke — look for [transcode] in the SW console or in the offscreen document console (offscreen has its own DevTools window).
  2. Enable workflow-side transcode (§8-2) as a backstop — even if an m4a leaks through, the next workflow run converts it to mp3.
  3. Regenerate a shorter audio overview in NotebookLM, or move audio hosting elsewhere (e.g., R2).

"is at X but expected Y" (HTTP 409) or "Rule was unable to be completed" (HTTP 403)

While bulk pushes a card every 20–30 seconds, GitHub Actions' auto: rebuild feed workflow can commit in parallel and race; or a GitHub repo ruleset validation can fail to complete within 10 seconds. Since v0.4.10, ghPut auto-retries with 1s/2s/4s backoff, so you usually don't see this. If you see 409 conflict (attempt 1/4), refreshing sha + retry in the activity log, the retry is doing its job — usually clears within 1–2 attempts. If all 4 retries fail, only that card is marked failed.

11. Permissions & privacy

PermissionPurpose
activeTab, scriptingInject the content script into the current NotebookLM tab + visit each notebook through background tabs / popup window during all-notebook sweep.
storageSave GitHub token / repo settings in the browser's local storage.
downloadsReceive NotebookLM audio + rename the file.
notificationsOne OS-level notification at the end of a long bulk download / sweep with the success/failure count, so you don't have to keep the admin page open.
alarmsWake the service worker every 30 seconds during long bulk tasks (5 min – 2+ hours) so it doesn't terminate while idle. The alarm is cleared automatically when the task ends.
debuggerSynthesize the click on NotebookLM's ⋮ → "Download" menu via Input.dispatchMouseEvent during bulk download. NotebookLM's isTrusted=true / user activation gate rejects programmatic .click(), so this is required. While attached, a yellow "debugging" banner shows on the popup window's notebook tab (Chrome's standard); it auto-detaches when the bulk run ends. Single-card popup downloads carry user activation through the call chain and don't need debugger.
offscreenClient-side m4a/mp4 → mp3 transcode. The SW environment lacks AudioContext, so the offscreen document handles decode + lamejs encode. Active only during a push, closed afterward.
host_permissions: notebooklm.google.comRead card metadata from NotebookLM page DOM.
host_permissions: *.googleusercontent.com, *.usercontent.google.com, accounts.google.com, lh3.google.comPass through the audio CDN / authentication redirect chain (details: IMPLEMENTATION_NOTES §2).
host_permissions: api.github.comPush audio / RSS to your repo.

Where the token is stored: chrome.storage.local. It is never sent to any external server; it is only used as the Authorization header on GitHub API calls. Removing the extension also clears it.

NotebookLM session cookies: when re-fetching audio, the extension uses credentials:"include" so cookies follow along through the redirect chain (lh3.googleusercontent → ServiceLogin → lh3.google → drum.usercontent.google). The extension does not store these cookies separately.
