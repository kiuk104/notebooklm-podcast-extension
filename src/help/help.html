NotebookLM Podcast Sync — 도움말

NotebookLM 음성개요를 본인 GitHub repo 로 push 해서 개인 팟캐스트 RSS 를 만드는 익스텐션 사용법.

목차
  1. 전체 흐름
  2. 처음 설정 (GitHub repo + PAT)
  3. 사용법 (단일 / 일괄 / 전체 스윕)
  4. RSS feed 생성
  5. 팟캐스트 메타 (제목 / 작성자 / 커버)
  6. 푸시된 에피소드 목록 관리 (편집 / 삭제)
  7. 보관 정책 (rolling window)
  8. Transcode (m4a → mp3)
  9. 파일명 규약
  10. 트러블슈팅
  11. 권한 & 프라이버시

1. 전체 흐름

NotebookLM 노트북 페이지 (음성개요 카드)
  → 익스텐션 [받기] 버튼
    → Chrome 이 audio 다운로드 (로컬 폴더에도 저장)
    → 동시에 익스텐션 SW 가 같은 audio 를 다시 fetch
      → GitHub Contents API 로 docs/episodes/ 에 PUT
        → (repo 의 GitHub Actions workflow 가) feed.xml 생성
          → 팟캐스트 앱 → 새 에피소드

한 번 셋업하면 그 다음부터는 NotebookLM 에 새 음성개요가 생길 때마다 익스텐션 아이콘 → [받기] 만 누르면 끝.

2. 처음 설정

2-1. 빈 public GitHub repo 만들기

  1. GitHub 에서 새 repo 생성. Public 으로. (RSS 가 외부 팟캐스트 앱에서 접근 가능해야 함.)
  2. Settings → Pages 에서 Source 를 main branch / /docs folder 로 활성화.
  3. 활성화 후 Pages URL 확인: https://<사용자>.github.io/<repo>/
  4. 최종 RSS URL 은: https://<사용자>.github.io/<repo>/feed.xml — 이걸 팟캐스트 앱에 등록.

2-2. Personal Access Token (PAT) 발급

  1. 새 PAT 발급 페이지 열기 (필요한 scope 가 미리 선택되어 있음).
  2. Note 에 식별 가능한 이름 (예: notebooklm-podcast-extension), Expiration 은 적당히.
  3. scope 는 repo 만 켜져 있으면 충분.
  4. [Generate token] → 표시되는 ghp_... 토큰 복사 (다시 못 봄).
토큰은 발급 직후 한 번만 보입니다. 페이지를 닫기 전에 익스텐션 옵션에 paste 하세요. 잃어버리면 다시 발급해야 합니다.

2-3. 익스텐션 관리 페이지에서 입력

  1. 익스텐션 아이콘 → 팝업 하단 ⚙ 관리 클릭.
  2. Token 에 위에서 받은 PAT paste.
  3. Repo 에 owner/name 형식 (예: kiuk104/my-notebooklm-podcast).
  4. RSS feed 생성 방식 은 기본값 GitHub Actions 에 위임 권장 (§4 참고).
  5. 커밋 이름/이메일은 비워 둬도 됨 (GitHub 기본값 사용).
  6. [저장] — 그 다음 [설정 검증] 을 한 번 눌러 토큰/repo 가 실제로 통하는지 확인. ✓ <사용자> → <repo> push 가능. 설정 정상. 이 떠야 OK.
[설정 검증] 은 GET /user + GET /repos/<owner>/<name> 두 번을 호출해서 토큰 자체 + repo 접근/push 권한을 한 번에 확인합니다. 401 / 404 / 권한 없음을 다운로드 흐름까지 가기 전에 잡아주는 가드.

3. 사용법

세 가지 모드가 있습니다 — 가벼운 단일 카드부터 모든 노트북 일괄 sweep 까지.

3-1. 단일 카드 받기 (개별)

  1. NotebookLM 에서 음성개요가 있는 노트북 페이지 열기 (https://notebooklm.google.com/notebook/<id>).
  2. 그 페이지에서 F5 한 번 — content script 가 inject 되도록 (배포 직후나 익스텐션 새로고침 직후 필요).
  3. 툴바의 익스텐션 아이콘 클릭 → [현재 노트북 스캔].
  4. 노트북 제목 / 생성일 + 음성개요 목록 확인.
  5. 받고 싶은 카드 옆 [받기] 클릭.
  6. 상태가 받는 중 → ⬇ 받음, push 중 → ✓ push 완료 로 진행.

3-2. 현재 노트북 일괄 받기 (체크박스 기반)

같은 [현재 노트북 스캔] 결과 화면에서 — 카드 옆에 체크박스가 있습니다.

  • 이미 repo 에 push 된 카드 (artifact UUID 매칭) 는 default 미체크 + ↻ 이미 받음 표시.
  • placeholder 제목 카드는 체크박스가 비활성 (다음 스캔에서 제목 확정되면 활성화).
  • 나머지는 default 체크 — 그대로 두면 새 카드만 받음.
  • 상단의 [전체 선택] 토글 + [선택 받기 (N)] 버튼으로 일괄 다운로드.
  • N 개를 순차로 처리 — 각 카드의 push 가 끝나면 다음 카드 시작 (NotebookLM 의 ⋮ → 다운로드 메뉴는 동시에 하나만 열려 race 방지).

3-3. 모든 노트북 스윕 (cross-notebook, v1 cron 동등)

NotebookLM 의 어떤 페이지에서든 popup 의 [모든 노트북 스캔] 클릭. 익스텐션이 두 단계로 동작합니다:

스캔 단계 (메인 윈도우의 background tab 사용):

  1. NotebookLM 홈 (/) 을 열어 모든 노트북 URL 수집.
  2. 각 노트북 페이지를 순차로 열어 음성개요 카드 수집 (5~10초/노트북).
  3. 탭 닫기 + 다음 노트북 진행. 200개 노트북이면 약 10~15분.
  4. 완료 후 노트북별로 그룹핑된 카드 목록이 popup 에 뜸 — 결과는 30분간 자동 보존되어, popup 을 닫았다 다시 열어도 같은 결과를 보여줍니다 (재스캔 안 해도 됨).
  5. 체크박스로 받을 카드 선택 (이미 받은 카드는 default 미체크) → [선택 받기].

다운로드 단계 (별도 popup window 사용):

  1. 익스텐션이 chrome.windows.create({type:"popup", focused:false}) 로 작은 popup window 를 띄움 (메인 윈도우 focus 그대로 유지). NotebookLM 의 download 트리거가 visibilityState='visible' + 사용자 input gesture 둘 다 요구하기 때문 — background tab 의 active:false 상태로는 download 가 발사되지 않습니다.
  2. 그 popup 안에서 노트북 탭을 차례로 열어 ⋮ → "다운로드" 메뉴를 chrome.debugger 의 Input.dispatchMouseEvent 로 클릭 — 브라우저 C++ 레벨에서 진짜 사용자 클릭 을 합성해 NotebookLM 이 isTrusted=true 로 인식.
  3. 각 카드: NotebookLM 이 audio 스트리밍 시작 → SW 가 같은 URL 을 재fetch → m4a/mp4 면 offscreen document 가 mp3 (64k mono) 로 transcode → GitHub 에 push.
  4. 모든 카드 완료 후 popup window 자동 닫힘.
스캔 후 자동 다운로드를 원하면 관리 페이지 (⚙ 관리) 의 스캔 후 신규 카드 자동 다운로드 체크박스를 켜세요. 켜면 [모든 노트북 스캔] 직후 repo 에 없는 카드들을 그대로 이어서 받습니다 (v1 cron 동등). 첫 사용 시 수십~수백 개가 한 번에 들어올 수 있으니 default 는 OFF — 우선 수동 검수 후 관리 페이지의 [직전 스캔 결과 → 신규 받기] 로 시작하는 게 안전.
"디버깅 중" 노란 배너 가 popup window 의 NotebookLM 탭 상단에 뜹니다 — Chrome 이 chrome.debugger 사용 익스텐션을 알리는 표준 표시. 정상 동작이며 popup 닫히면 자동 해제. 메인 윈도우엔 영향 없음.
Chrome 기본 다운로드 폴더에도 같은 파일이 저장됩니다 (오프라인 백업). repo 에는 docs/episodes/ 아래에 push 됩니다.

3-4. 진행 중 popup 닫으면?

3-2 (단일 노트북 일괄): popup 의 JS 가 loop 를 돌리므로 닫으면 멈춤. 이미 시작된 다운로드는 background SW 에서 계속 처리.

3-3 (모든 노트북 sweep): background SW 에서 orchestration 하므로 popup 닫혀도 계속 진행. popup 재오픈 시 카드 list 자체는 복원되지 않지만 — 관리 페이지 (⚙ 관리) 상단의 진행 모니터 에서 현재 상태 (스캔/다운로드 단계, 진행률, 경과 시간, 에러) 가 라이브로 보입니다. background 가 chrome.storage.session 에 상태를 저장하므로 관리 페이지를 닫고 다시 열어도 진행 중인 작업은 그대로 노출.

3-5. 진행 모니터 (관리 페이지)

모든 노트북 sweep 또는 일괄 다운로드는 5~10분 걸릴 수 있어 popup 만으로는 진행 상황 확인이 불편합니다. 관리 페이지 상단의 진행 모니터 패널 이:

  • 현재 작업 종류 (모든 노트북 스캔 / 일괄 다운로드) + 상태 배지 (진행 중 / 완료 / 실패)
  • 경과 시간 (초 → 분 → 시간 단위로 자동 변환)
  • 현재 단계 메시지 (예: "노트북 12/30 스캔 중…")
  • 진행률 막대 (done/total 비율)
  • 통계 요약 (노트북 N 개 · 카드 N 개 · 성공 N · 실패 N)
  • 실패 목록 — 어느 노트북/카드에서 어떤 이유로 실패했는지 (max 20개, 위에서부터 오래된 것)
  • 최근 GitHub push 활동 로그 — 마지막 30 건의 push 결과를 라이브 표시. 4 가지 아이콘으로 구분:
    • ✓ 성공 (초록): GitHub 으로 PUT 정상 완료. 파일 크기와 feed 갱신 여부 함께 표시.
    • ↻ dedup 스킵 (회색): 같은 artifact UUID 의 파일이 이미 저장소에 있어 PUT 건너뜀 — 정상 동작입니다.
    • ⚠ GitHub 설정 없음 (노란 배경): 옵션 페이지의 token 또는 repo 가 비어있어 push 시도가 즉시 거절됨. 실제로 GitHub 으로 호출이 가지 않은 상태이므로 GitHub 백업이 의도였다면 [GitHub 설정] 을 채우고 다시 받기 하셔야 합니다. Chrome 다운로드 자체는 이와 무관하게 정상 진행.
    • ✗ 실패 (빨강): push 시도는 했지만 네트워크 / 권한 / 저장소 문제로 거절됨. 실패 사유가 줄 끝에 표시.
    헤더에 누적 카운트와 push 된 총 byte (예: ✓ 12 · ↻ 3 · ⚠ 2 · ✗ 1 · 142.7MB).

작업이 idle / completed / failed 상태일 때만 [초기화] 버튼이 노출 — 누르면 패널이 사라집니다 (다음 작업 시작하면 자동으로 다시 표시).

패널은 작업이 없을 때 (idle) 자동으로 숨겨지므로 평소엔 옵션 폼만 보입니다.

3-6. 직전 스캔 결과 패널 + [신규 받기]

모든 노트북 sweep 이 완료되면 그 결과가 chrome.storage.session 에 30분간 보존됩니다. 관리 페이지 폼 아래에 "직전 스캔 결과" 패널이 자동으로 등장:

  • 요약: 노트북 N개 · 카드 N개 · 신규 N개 + 스캔 후 경과 시간.
  • [신규 N개 받기] 버튼 — popup 안 열고 관리 페이지에서 바로 bulk 다운로드 시작. 진행 상황은 위쪽 모니터에 자동 노출.
  • [지우기] 버튼 — 저장된 스캔 결과 삭제 (다음 sweep 시작 시 자동 갱신됨).

같은 결과는 popup 도 자동 복원 — popup 닫혔다 다시 열면 재스캔 없이 cards list 가 그대로 표시됩니다 (30분 freshness 가드).

4. RSS feed 생성

음성개요 m4a/mp3 파일이 repo 에 올라가는 것만으로는 팟캐스트 앱이 인식 못 합니다. docs/feed.xml (RSS) 이 같이 있어야 합니다. 익스텐션 옵션의 RSS feed 생성 방식 으로 두 갈래 중 하나를 택하세요.

4-1. GitHub Actions 에 위임 (기본값, 권장)

repo 에 워크플로 파일 (.github/workflows/build-feed.yml) 을 두면 audio 가 push 될 때마다 GitHub 가 알아서 feed.xml 을 다시 만들고 commit 합니다. 익스텐션은 audio push 만 하므로 가볍고, 워크플로 로직을 사용자가 자유롭게 커스터마이즈할 수 있습니다.

표준 한 벌 example: 익스텐션 repo 의 examples/feed-builder/ 폴더에 그대로 복사해 쓸 수 있는 4 개 파일이 있습니다 (워크플로, 빌드 스크립트, podcast.json, README). 본인 RSS 호스팅 repo 에 같은 경로 (.github/workflows/, scripts/, docs/podcast.json) 로 복사 → docs/podcast.json 의 제목/오너 정보만 본인 것으로 수정 → push 하면 첫 audio 가 들어왔을 때 (또는 Actions 탭에서 [Run workflow] 로 수동 트리거) feed.xml 이 자동 생성됩니다.

외부 의존성 없는 Python 표준 라이브러리만 사용하므로 GitHub Actions 의 setup-python 한 단계만 있으면 빌드됩니다. 자세한 셋업 / 트러블슈팅은 example 폴더의 README 참조.

4-2. 익스텐션이 매 push 시마다 직접 생성

익스텐션이 audio push 직후 본인이 직접 episodes 디렉토리를 list 해서 feed.xml 을 만들어 같이 PUT 합니다. 워크플로 셋업 부담이 없는 대신 매번 list + XML 조립을 익스텐션이 부담합니다. 매 audio 카드의 [받기] 한 번이 두 번의 GitHub PUT (audio + feed) 으로 이어집니다.

이 모드도 4-1 과 같은 메타 source 를 씁니다 — repo 의 docs/podcast.json 이 있으면 그걸 읽어 RSS 의 title/owner/image 등을 채웁니다. 없으면 default 메타 (title = "NotebookLM Podcast", language = "ko", owner 비어 있음) 로 진행하고 SW 콘솔에 경고 한 번 출력. 팟캐스트 앱 등록을 위해서는 docs/podcast.json 을 추가하는 것이 권장됩니다 (포맷은 example 그대로).

BASE_URL 은 익스텐션 옵션의 owner/name 에서 자동 조립 (https://<owner>.github.io/<name>/) — custom domain 을 쓰는 경우 4-1 모드 (워크플로) 가 더 적합합니다.

5. 팟캐스트 메타 (제목 / 작성자 / 커버 이미지)

팟캐스트 앱에 노출되는 채널 정보 (제목, 설명, 작성자, 커버 이미지, 카테고리) 는 본인 repo 의 docs/podcast.json 에 저장됩니다. 관리 페이지의 "팟캐스트 메타데이터" 섹션에서 폼으로 편집 가능 — repo 를 직접 열어서 JSON 수정할 필요 없음.

5-1. 메타 편집

  1. 관리 페이지 (⚙ 관리) 열면 GitHub Token + Repo 가 저장된 상태에서 자동으로 현재 podcast.json 을 가져와 폼에 채웁니다.
  2. 제목 / 설명 / 작성자 이름 · 이메일 / 언어 / 카테고리 / 명시적 콘텐츠 / 커버 이미지 URL 수정.
  3. [메타 저장] 클릭 → repo 의 docs/podcast.json 이 갱신됨 → 워크플로가 자동 트리거되어 feed.xml 이 새 메타로 재빌드됩니다.
  4. 팟캐스트 앱이 다음 refresh 때 새 정보를 받습니다 (보통 수십 분~몇 시간).

5-2. 커버 이미지 업로드

iTunes/Apple Podcasts 표준 — 1400×1400 이상 JPG/PNG. 일부 앱은 작은 이미지 거절 (스크린샷의 분홍 "P" 같은 placeholder 가 그 케이스).

  1. 커버 이미지 행의 파일 선택 클릭 → 로컬 JPG/PNG 선택 (max 5MB).
  2. 익스텐션이 본인 repo 의 docs/cover.{jpg|png} 로 PUT 합니다 (Pages 가 자동으로 서빙).
  3. 이미지 URL 필드가 자동으로 https://<owner>.github.io/<repo>/cover.{jpg|png} 로 채워짐.
  4. [메타 저장] 까지 눌러야 podcast.json 의 image 필드가 그 URL 로 갱신되어 feed.xml 에 반영됩니다.
외부 이미지 호스팅 (예: Imgur, Cloudinary) URL 을 직접 입력해도 동작합니다 — 단 그 호스팅이 영구적이어야 함. GitHub Pages 호스팅 (위 업로드 방식) 이 가장 안정적.

5-3. 폼에 노출되지 않는 필드

retention (보관 정책, §7) 과 transcode (m4a→mp3, §8) 는 폼에 없습니다 — 자주 바꾸지 않는 기술 옵션이라 podcast.json 직접 편집 권장. 메타 [저장] 시 이 필드들은 그대로 보존됩니다 (덮어쓰지 않음).

6. 푸시된 에피소드 목록 관리

관리 페이지의 "푸시된 에피소드" 섹션은 본인 repo 의 docs/episodes/ 에 저장된 모든 음성개요를 표 형태로 보여줍니다 — v1 admin 페이지의 episode 표와 같은 구조. token + repo 가 저장된 상태에서 페이지 진입 시 자동 fetch.

6-1. 표 컬럼과 정보

  • 날짜: 파일명 prefix 의 YYYYMMDD 를 ISO 형식으로.
  • 노트북: 파일명에서 추출한 노트북 슬러그 (하이픈을 공백으로).
  • 제목: 음성개요 제목 슬러그 (마우스 hover 시 전체 파일명 표시).
  • 형식: m4a / mp3 / mp4 컬러 태그 — 큰 m4a 는 노란색, transcode 된 mp3 는 초록색이라 한눈에 식별.
  • 크기: 바이트 → MB 표시.

6-2. 정렬 / 그룹화

  • 모든 컬럼 헤더 클릭 → asc / desc 토글. 화살표가 ▲▼ → ▲ / ▼ 로 강조.
  • [정렬 초기화 (날짜 ↓)] — 기본 (최신순) 으로 한 번에 복귀.
  • [노트북별 그룹화] 토글 → 같은 노트북 카드들이 묶이고 헤더 row 에 📓 노트북명 (N개) 표시.

6-3. 편집 (NotebookLM 원본으로 이동)

각 행의 [편집 ↗] 버튼은 새 탭 으로 해당 NotebookLM 노트북을 엽니다. 음성개요 제목이나 내용 편집은 NotebookLM 이 source of truth — 거기서 수정한 뒤 이쪽에서 옛 카드를 [삭제] 하면 다음 sweep 에서 새 제목으로 다시 push 됩니다.

[편집 ↗] 이 비활성 (회색) 이면 직전 스캔 결과가 없어서 노트북 URL 을 매칭 못 한 상태입니다. popup 의 [모든 노트북 스캔] 한 번 돌리면 노트북 URL 매핑이 30분간 유지되어 활성화됩니다.

6-4. 삭제 (단일 / 일괄)

  • 각 행의 [삭제] — 단일 ghDelete (확인 dialog → 1번 호출 → ✓).
  • 좌측 체크박스 + 상단의 [선택 삭제] — 다중 선택 후 일괄. 진행 중에 status 표시 (1/N → 2/N…). 부분 실패 시 성공/실패 카운트 표시.
  • 제일 위 전체 선택 체크박스 — 한 번에 모든 row 토글.
  • 삭제 후 자동으로 [↻ 새로고침] 트리거 → 표 갱신.
삭제는 repo 의 파일만 제거 — NotebookLM 의 카드는 그대로 살아 있습니다. 다음 sweep 시 [받기] 를 누르면 다시 받아옵니다 (중복 push 는 shortId dedup 으로 알아서 방지). 잘못 받은 카드 / 오디오 placeholder 상태로 받힌 카드 정리에 유용.

7. 보관 정책 (rolling window)

repo 용량을 통제하려면 docs/podcast.json 에 retention 필드를 추가하세요. 두 RSS 모드 (4-1, 4-2) 모두 같은 정책을 따르므로, 모드를 바꿔도 정리 동작은 동일합니다.

{
  "title": "...",
  ...
  "retention": {
    "maxItems": 50,
    "maxAgeDays": 365
  }
}
필드의미
maxItems최근 N 개의 episode 만 유지. 그보다 오래된 파일은 build 시점에 자동 삭제.
maxAgeDays오늘로부터 N 일 이내 episode 만 유지.
maxTotalMBdocs/episodes/ 합계 크기 상한 (MB). 최신 순으로 누적해 cap 넘기면 거기서 자름. GitHub Pages 1 GB artifact 한도 회피용. 64k mono mp3 평균 ~5 MB 기준 900 MB 면 ~180 편 보존. 단일 파일이 cap 보다 커도 최신 1편은 무조건 유지.

셋 다 설정하면 모두 통과해야 유지 (AND) — 더 짧은 정책이 실질적으로 적용됩니다. 한 쪽만 쓰려면 다른 쪽을 빼거나 0 으로. retention 필드 자체를 제거하면 정리 비활성 (모든 episode 영구 보관).

NotebookLM 의 카드 자체를 지우는 것과는 무관합니다 — repo 의 파일만 정리. 보관 정책 밖으로 나간 episode 는 RSS 에서 사라지지만 NotebookLM 에 카드가 살아 있다면 [받기] 를 다시 누를 때 또 push 됩니다.

8. Transcode (m4a → mp3)

NotebookLM 의 m4a 는 256k stereo 라 한 시간에 ~22MB. 음성개요는 사람 목소리 위주라 64k mono mp3 (~5MB) 로도 충분히 들립니다 — repo 1GB 한도가 약 4배 늘어나는 효과. 게다가 GitHub Contents API 는 ~37 MiB / Git Data API blob 도 ~40 MiB 가 실질 상한이라 NotebookLM 의 1.5~2.5h 음성개요 (40~50 MB) 가 *둘 다 거절* 되는 사각지대 — transcode 가 그 사각지대를 회피하는 핵심 수단.

두 가지 모드가 있고 함께 켜져도 무방 (먼저 적용된 쪽이 이미 mp3 로 만들어 두면 다음 단계는 no-op).

8-1. 익스텐션 측 (offscreen + lamejs, 자동 적용)

v0.4.11 부터 익스텐션이 *자체적으로* m4a/mp4 를 mp3 로 변환한 뒤 GitHub 에 push 합니다. 별도 설정 불필요 — m4a/mp4 형식이면 자동.

  • 위치: SW 가 audio fetch 후 offscreen document 로 ArrayBuffer 전달 → AudioContext.decodeAudioData 로 PCM 디코드 → lamejs Mp3Encoder 로 64k mono mp3 인코드 → SW 로 회신 → ghPut.
  • 속도: 30분 분량 ~10초, 60분 분량 ~20초. SW 메모리 peak 50 MB 입력 + 5 MB 출력.
  • 파일명: .m4a / .mp4 가 자동으로 .mp3 로 교체되어 push.
  • 실패 시 fallback: transcode 가 실패하면 원본 m4a 그대로 push 시도 — Git Data API blob 한계에 막히면 그 카드만 fail (드뭄).
이미 repo 에 들어가 있는 m4a/mp4 는 익스텐션 측 transcode 의 대상이 아닙니다 (transcode 는 push 흐름에서만 적용). 옛 m4a/mp4 를 mp3 로 정리하려면 아래 §8-2 의 워크플로 측 transcode 를 켜세요 — 다음 워크플로 트리거 때 docs/episodes/ 의 모든 옛 m4a/mp4 를 mp3 로 변환합니다.

8-2. 워크플로 측 native ffmpeg (백워드 호환)

docs/podcast.json 의 transcode 필드를 켜면 워크플로의 transcode step 이 docs/episodes/ 안 m4a/mp4 를 같은 이름의 mp3 로 변환합니다 (원본 삭제). ubuntu-latest 의 native ffmpeg (libmp3lame 포함) 가 처리해서 1시간 audio 가 5~10초. RSS 모드는 4-1 (Actions 위임) 사용 전제. 옛 v0.4.11 이전 버전이 push 한 m4a 를 정리할 때 유용 — 한 번 켜고 다음 push 한 번이면 모두 mp3 로 일괄 변환됩니다.

{
  ...
  "transcode": {
    "enabled": true,
    "bitrate": "64k",
    "mono": true
  }
}
필드의미
enabledtrue 일 때만 변환 시도. 기본 false.
bitrate"64k" / "96k" / "128k" 등. 음성 위주면 "64k", 음악/효과음 비중이 높으면 "96k" 이상.
monotrue 면 -ac 1 로 다운믹스. NotebookLM 음성개요는 기본 mono 라 stereo 유지의 의미가 작음.
익스텐션 직접 RSS 모드 (4-2) 와 함께 쓰면 잠시 m4a feed 가 노출됨: 익스텐션이 m4a 를 push 한 직후 m4a 기준으로 RSS 가 한 번 빌드되고, 그 다음 워크플로가 트리거되어 mp3 로 transcode + RSS 재빌드. 그 사이 (보통 30초~1분) 팟캐스트 앱이 m4a URL 을 받아갈 수 있습니다. transcode 를 쓸 거면 RSS 모드도 4-1 (Actions 위임) 로 통일하는 게 깔끔.

익스텐션 내장 (ffmpeg.wasm) 모드: 미구현. 패키지 +25MB / SW 메모리 100~200MB / 첫 [받기] 응답 30초~수분 등 트레이드오프가 커서 후순위. 워크플로 셋업이 어려운 사용자만을 위한 옵션.

9. 파일명 규약

YYYYMMDD__노트북-슬러그__shortId__제목-슬러그.{m4a|mp3}
구간의미
YYYYMMDDNotebookLM 노트북의 cover 생성일 (페이지 cover 영역의 날짜 표시).
노트북-슬러그노트북 제목을 한글/영숫자만 남기고 40자로 컷.
shortId카드의 NotebookLM artifact UUID 첫 8자 (16진수). 제목과 무관하게 카드별로 고정이라 dedup 키로 사용 — 같은 카드를 다시 받거나 NotebookLM 에서 노트북 이름 / 카드 제목이 사후 변경되어도 GitHub 측 중복 push 가 방지됨 (PUT 직후 재클릭 케이스도 포함 — GET 응답을 캐시하지 않아 항상 최신 listing 으로 매칭).
제목-슬러그음성개요 카드 제목을 같은 규칙으로 40자로 컷.

40자 컷은 Windows MAX_PATH (260) + GitHub path 255-byte 제한 가드입니다. 한글 1자가 UTF-8 3 byte 라 제목이 길 때 GitHub 가 거절하는 사고를 방지.

옛 포맷과의 호환: v0.4.0 이전 버전이 push 한 파일은 shortId 없이 3-segment YYYYMMDD__노트북__제목.{ext} 로 저장돼 있을 수 있습니다. RSS 빌더 (익스텐션 / GitHub Actions 워크플로) 모두 두 포맷을 동시에 인식하므로 그대로 두어도 무방합니다. 새 push 부터만 4-segment 포맷이 적용됩니다.

10. 트러블슈팅

"현재 탭이 NotebookLM 노트북 페이지가 아닙니다"

NotebookLM 의 노트북 상세 페이지 (/notebook/<id>) 에서만 동작합니다. 홈 / 검색 페이지에서는 스캔 안 됨.

"응답 없음 — 페이지를 새로고침하세요"

NotebookLM 페이지를 익스텐션 설치/새로고침 전에 열었으면 content script 가 주입 안 된 상태. 그 페이지에서 F5.

push 실패: 401 Bad credentials 또는 권한 부족

  1. 관리 페이지에서 [설정 검증] 을 한 번 눌러 어디서 막히는지 확인 — 토큰 401 / repo 404 / push 권한 없음 중 하나로 분류됨.
  2. 토큰 401 이면: token 필드 비우고 새로 paste (보이지 않는 trailing 공백 제거). 그래도 안 되면 PAT 만료 — 새로 발급 (§2-2).
  3. repo 404 이면: owner/name 오타 또는 private repo 인데 토큰 권한이 그 repo 를 못 봄. fine-grained PAT 의 repository access 설정 확인.
  4. push 권한 없음이면: classic PAT 는 repo scope, fine-grained PAT 는 해당 repo 에 Contents: Read and write 권한 필요.

같은 음성개요가 두 번 받아짐 (예: __audio-0.mp3, __실제-제목.mp3)

NotebookLM 이 음성개요 생성 직후 제목을 audio 0, audio 1 같은 플레이스홀더로 잠시 보여주다가 비동기로 실제 제목으로 교체합니다. 플레이스홀더 상태에서 받으면 같은 audio 를 두 번 받게 될 수 있음. 잠시 기다렸다가 제목이 확정된 뒤 받기 권장. 자세한 내용은 IMPLEMENTATION_NOTES.md §1.

"Chrome 탭 API 잠김" 또는 "Tabs cannot be edited right now"

모든 노트북 sweep 중 다수의 노트북이 같은 메시지로 줄줄이 실패하는 케이스. 실제 사용자 드래그뿐 아니라 빠른 연속 탭 create/close, 다른 탭 관리 익스텐션과의 충돌, Chrome 내부 rate limit 에서 발생.

익스텐션이 자동으로 5회까지 backoff (500ms → 8s) retry 합니다. 5회 연속 실패하면 sweep 자체를 abort 하고 안내 메시지를 표시 — 그 시점까지 성공한 결과는 보존되어 [신규 받기] 로 활용 가능.

대응: (a) 탭바를 클릭/드래그하지 않은 상태에서 재시도 (b) 다른 탭 관리 익스텐션 (OneTab, tab grouping 류) 을 잠시 비활성화 (c) 잠시 기다렸다가 다시 시도. 자세한 분석은 IMPLEMENTATION_NOTES.md §5.

다운로드는 됐는데 GitHub 에 안 올라감

SW devtools console 확인:

  1. chrome://extensions/ 에서 익스텐션 카드의 service worker 링크 클릭.
  2. console 에 [push] ... 로그 보임 — fetch / push 단계별 상태 확인.
  3. 에러 메시지 (host, status) 가 다음 차단 호스트나 권한 문제를 노출함.

bulk 가 모든 카드에서 "push 응답 타임아웃"

Sweep 직후 bulk 다운로드가 시작됐는데 카드마다 push 응답 타임아웃 → SW 콘솔에 [push] SW fetch host=... 로그가 *전혀* 안 찍히는 케이스. 이건 NotebookLM 이 background tab 의 download 트리거를 거부했다는 신호 — popup window 가 안 떴거나 chrome.debugger attach 가 실패한 상태일 가능성. chrome://extensions/ 의 본 익스텐션 카드 → 권한 (debugger / offscreen) 이 부여돼 있는지 확인 후 익스텐션 새로고침. 자세한 매커니즘: IMPLEMENTATION_NOTES.md §9, §10.

특정 카드만 "이 file 은 ~XX MB 가 GitHub blob API 한계 (~40MB) 초과"

NotebookLM 이 1.5~2.5 시간짜리 음성개요로 만든 m4a 가 GitHub Contents API (~37 MiB) 와 Git Data API blob (~40 MiB) 사이 사각지대에 떨어진 케이스. v0.4.11 의 client-side transcode 가 자동으로 mp3 64k mono 로 줄여 회피하는데, 그 transcode 가 실패하면 이 에러가 노출됩니다. 흔치 않지만 발생 시:

  1. transcode 자체가 깨졌는지 → SW 콘솔의 [transcode] 또는 offscreen document 콘솔 확인 (offscreen 은 별도 DevTools 창).
  2. 워크플로 측 transcode (§8-2) 를 같이 켜서 backstop — m4a 가 어쩌다 push 됐어도 다음 워크플로 트리거 때 mp3 로 변환됨.
  3. NotebookLM 에서 더 짧은 음성개요로 재생성, 또는 외부 호스팅 (R2 등) 으로 이동.

"is at X but expected Y" (HTTP 409) 또는 "Rule was unable to be completed" (HTTP 403)

bulk 가 매 20-30초씩 카드를 push 하는 동안 GitHub Actions 의 auto: rebuild feed 워크플로가 동시에 commit 을 만들어 race 가 발생한 케이스. 또는 GitHub repo ruleset 검증이 10초 안에 못 끝난 timeout. v0.4.10+ 부터 ghPut 가 자동으로 1s/2s/4s backoff 재시도하므로 보통 사용자가 볼 일 없습니다. 활동 로그에 409 conflict (attempt 1/4), refreshing sha + retry 같은 줄이 보이면 retry 가 작동 중인 것 — 보통 1-2회 안에 통과. 4회 모두 실패하면 그 카드만 fail 표시.
