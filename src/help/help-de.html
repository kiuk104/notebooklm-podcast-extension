NotebookLM Podcast Sync — Hilfe

Eine Chrome-Erweiterung, die NotebookLMs Audio-Übersichten in dein eigenes GitHub-Repo pusht und daraus einen persönlichen Podcast-RSS-Feed macht.

1. Funktionsweise

NotebookLM-Notebook-Seite (Audio-Übersichts-Karten)
  → Erweiterung [Herunterladen]
    → Chrome lädt die Audio-Datei (auch in den lokalen Ordner)
    → Parallel holt der Service Worker dieselbe Audio-Datei nochmals
      → PUT in docs/episodes/ via GitHub Contents API
        → (GitHub-Actions-Workflow im Repo) baut feed.xml neu
          → Podcast-App → neue Episode

Nach dem einmaligen Setup reicht für jede neue Audio-Übersicht ein Klick auf [Herunterladen] in der Erweiterung.

2. Erstmaliges Setup

2-1. Leeres öffentliches GitHub-Repo erstellen

  1. Erstelle ein neues Repo auf GitHub. Public (der RSS-Feed muss von Podcast-Apps erreichbar sein).
  2. Öffne Settings → Pages und setze Source auf den main-Branch / Ordner /docs.
  3. Notiere die Pages-URL: https://<benutzer>.github.io/<repo>/
  4. Die endgültige RSS-URL lautet: https://<benutzer>.github.io/<repo>/feed.xml — abonniere diese in deiner Podcast-App.

2-2. Personal Access Token (PAT) erzeugen

  1. Öffne die Seite für neue PAT (der nötige Scope ist vorausgewählt).
  2. Vergib einen aussagekräftigen Note (z. B. notebooklm-podcast-extension) und wähle ein Ablaufdatum.
  3. Es genügt der Scope repo.
  4. Klicke [Generate token] → kopiere den angezeigten ghp_...-Token (er wird nicht erneut angezeigt).
Der Token wird nur einmal angezeigt. Füge ihn in die Erweiterungseinstellungen ein, bevor du die Seite schließt. Verloren? Dann muss ein neuer erzeugt werden.

2-3. Eingaben auf der Verwaltungsseite

  1. Erweiterungssymbol klicken → unten im Popup ⚙ Verwaltung.
  2. PAT in das Feld Token einfügen.
  3. Repo im Format owner/name eingeben (z. B. kiuk104/my-notebooklm-podcast).
  4. RSS-Feed-Modus: belasse den Standardwert An GitHub Actions delegieren (siehe §4).
  5. Commit-Name/E-Mail darfst du leer lassen (GitHub-Standardwerte werden verwendet).
  6. [Speichern] klicken, dann [Prüfen], um Token + Repo zu verifizieren. ✓ <benutzer> → <repo> Push möglich. Alles korrekt. bedeutet OK.
[Prüfen] ruft GET /user + GET /repos/<owner>/<name> auf, um den Token sowie Repo-Zugriff/Push-Berechtigung in einem Schritt zu validieren. Fängt 401 / 404 / fehlende Push-Rechte ab, bevor irgendein Download läuft.

3. Benutzung

Drei Modi — von einer einzelnen Karte bis zum kompletten Sweep über alle Notebooks.

3-1. Einzelne Karte herunterladen

  1. Öffne in NotebookLM eine Notebook-Seite mit Audio-Übersicht (https://notebooklm.google.com/notebook/<id>).
  2. Drücke einmal F5 auf dieser Seite, damit das Content-Script injiziert wird (nötig nach Erweiterungs-Installation/Neuladen).
  3. Erweiterungssymbol in der Symbolleiste klicken → [Aktuelles Notebook scannen].
  4. Notebook-Titel / Erstellungsdatum + Liste der Audio-Übersichten erscheint.
  5. Neben der gewünschten Karte auf [Herunterladen] klicken.
  6. Status: wird heruntergeladen → ⬇ heruntergeladen, wird gepusht → ✓ Push erfolgreich.

3-2. Aktuelles Notebook im Bündel (Checkboxen)

Im selben [Aktuelles Notebook scannen]-Ergebnis steht neben jeder Karte eine Checkbox.

  • Bereits ins Repo gepushte Karten (per Artifact-UUID erkannt) sind standardmäßig nicht ausgewählt und tragen das Label ↻ bereits gepusht.
  • Karten mit Platzhalter-Titel haben deaktivierte Checkboxen (werden bei einem späteren Scan, sobald der Titel feststeht, wieder aktiv).
  • Der Rest ist standardmäßig ausgewählt — so werden nur neue Karten geholt.
  • Oben [Alle auswählen] + [Auswahl herunterladen (N)] für Bündel-Download.
  • Die N Karten werden sequenziell verarbeitet — nach erfolgreichem Push der einen startet die nächste (NotebookLMs ⋮ → Download-Menü erlaubt nur eines gleichzeitig, das verhindert Race Conditions).

3-3. Sweep über alle Notebooks (entspricht v1-Cron)

Auf einer beliebigen NotebookLM-Seite im Popup auf [Alle Notebooks scannen] klicken. Die Erweiterung läuft in zwei Phasen:

Scan-Phase (Hintergrund-Tabs im Hauptfenster):

  1. Öffnet die NotebookLM-Startseite (/) und sammelt alle Notebook-URLs.
  2. Öffnet jedes Notebook nacheinander und sammelt die Audio-Karten (5–10 s pro Notebook).
  3. Schließt den Tab und macht weiter. 200 Notebooks ≈ 10–15 Minuten.
  4. Die nach Notebook gruppierte Kartenliste erscheint im Popup. Das Ergebnis wird 30 Minuten lang zwischengespeichert — Popup schließen und wieder öffnen erfordert keinen erneuten Scan.
  5. Wähle per Checkbox aus, was geladen werden soll (bereits gepushte Karten sind abgewählt) → [Auswahl herunterladen].

Download-Phase (eigenes Popup-Fenster):

  1. Die Erweiterung öffnet ein kleines Popup-Fenster über chrome.windows.create({type:"popup", focused:false}). Ab v0.4.42 wird es am linken Bildschirmrand positioniert (left:-399, top:0) — größtenteils außerhalb des Bildschirms, erfüllt aber Chromes „≥50 % der Fensterfläche müssen sichtbar sein"-Regel und behält visibilityState='visible'. focused:false stellt sicher, dass das Hauptfenster den Fokus behält. NotebookLMs Download-Trigger verlangt sowohl visibilityState='visible' als auch eine echte User-Geste — ein Background-Tab im active:false-Zustand löst keinen Download aus.
  2. Innerhalb dieses Popups öffnet die Erweiterung jedes Notebook nacheinander und klickt das ⋮ → "Herunterladen"-Menü mittels chrome.debugger + Input.dispatchMouseEvent — auf C++-Browserebene wird ein echter Nutzer-Klick synthetisiert, sodass NotebookLM isTrusted=true sieht.
  3. Pro Karte: NotebookLM startet das Audio-Streaming → der SW holt dieselbe URL erneut → ist es m4a/mp4, transcodiert das Offscreen-Dokument zu mp3 (64k Mono) → Push zu GitHub.
  4. Das Popup-Fenster schließt sich automatisch, sobald alle Karten fertig sind.
Für automatischen Download neuer Karten nach dem Scan aktiviere auf der Verwaltungsseite (⚙ Verwaltung) die Option Neue Karten nach dem Scan automatisch herunterladen. Direkt nach [Alle Notebooks scannen] werden Karten, die noch nicht im Repo sind, geladen — entspricht dem v1-Cron. Beim ersten Mal können Dutzende bis Hunderte zugleich kommen, deshalb Standard AUS — sicherer ist es, das Ergebnis erst zu sichten und dann [Letzter Scan → Neue laden] manuell auszulösen.
Im NotebookLM-Tab des Popup-Fensters erscheint oben ein gelber „Debugging"-Hinweis — Chromes Standardanzeige für Erweiterungen, die chrome.debugger verwenden. Normales Verhalten; verschwindet, sobald das Popup schließt. Hauptfenster ist nicht betroffen.
Dieselbe Audio-Datei wird auch in Chromes Standard-Download-Ordner gespeichert (Offline-Backup). Im Repo landet sie unter docs/episodes/.

3-4. Popup während eines Vorgangs schließen?

3-2 (Bündel im aktuellen Notebook): Das Popup-JS treibt die Schleife an — Schließen stoppt neue Downloads. Bereits gestartete Downloads werden im Hintergrund-SW abgeschlossen.

3-3 (Sweep über alle Notebooks): wird komplett im Hintergrund-SW orchestriert — Schließen unterbricht nichts. Beim erneuten Öffnen des Popups wird die Kartenliste nicht wiederhergestellt — stattdessen zeigt der Fortschrittsmonitor auf der Verwaltungsseite (⚙ Verwaltung) den Live-Stand (Scan-/Download-Phase, Fortschritt, verstrichene Zeit, Fehler). Da der Hintergrund den Status in chrome.storage.session speichert, bleibt die laufende Aufgabe sichtbar, selbst wenn die Verwaltungsseite geschlossen und wieder geöffnet wird.

3-5. Fortschrittsmonitor (Verwaltungsseite)

Ein Sweep oder Bündel-Download kann 5–10 Minuten (oder länger) dauern, und das Popup allein ist dafür unhandlich. Das Fortschritts-Panel oben auf der Verwaltungsseite zeigt:

  • Aktueller Aufgaben-Typ (Alle Notebooks scannen / Massendownload) + Status-Badge (Läuft / Fertig / Fehler)
  • Verstrichene Zeit (automatisch Sekunden → Minuten → Stunden)
  • Phasen-Meldung (z. B. „Notebook 12/30 wird gescannt…")
  • Fortschrittsbalken (done/total)
  • Statistik-Zusammenfassung (N Notebooks · N Karten · N OK · N fehlgeschlagen)
  • Fehlerliste — welches Notebook/Karte aus welchem Grund fehlschlug (max. 20, älteste oben)
  • Letzte GitHub-Push-Aktivität — die letzten 30 Push-Resultate live. Vier Symbole unterscheiden das Ergebnis:
    • ✓ ok (grün): PUT auf GitHub erfolgreich. Dateigröße und Feed-Update-Status werden mit angezeigt.
    • ↻ Dedup-Skip (grau): Eine Datei mit derselben artifact-UUID liegt bereits im Repo, daher wurde PUT übersprungen — normales Verhalten.
    • ⚠ Keine GitHub-Konfig (gelber Hintergrund): Token oder Repo auf der Optionen-Seite ist leer, der Push wurde sofort abgelehnt. Kein HTTP-Aufruf hat GitHub erreicht. Falls eine Sicherung auf GitHub gewünscht war, [GitHub-Einstellungen] ausfüllen und erneut laden. Der Chrome-Download selbst ist davon unberührt.
    • ✗ fehlgeschlagen (rot): Push wurde versucht, aber wegen Netzwerk / Berechtigungen / Repository-Problemen abgelehnt. Fehlerursache am Zeilenende.
    Header zeigt Summen und insgesamt gepushte Bytes (z. B. ✓ 12 · ↻ 3 · ⚠ 2 · ✗ 1 · 142,7 MB).

[Zurücksetzen] erscheint nur bei idle / fertig / fehlgeschlagen — Klick blendet das Panel aus (nächste Aufgabe zeigt es automatisch wieder).

Ohne laufende Aufgabe ist das Panel ausgeblendet, sodass das Formular die volle Fläche bekommt.

3-6. Letztes Scan-Ergebnis + [Neue laden]

Ein abgeschlossener Sweep wird 30 Minuten in chrome.storage.session behalten. Unterhalb des Formulars erscheint das „Letztes Scan-Ergebnis"-Panel:

  • Zusammenfassung: N Notebooks · N Karten · N neu + wie lange der Scan zurückliegt.
  • [N neue laden] — Bündel-Download direkt auf der Verwaltungsseite starten (kein Popup nötig). Fortschritt erscheint im Monitor oben.
  • [Löschen] — gespeichertes Ergebnis verwerfen (nächster Sweep ersetzt es ohnehin).

Das gleiche Ergebnis wird auch im Popup automatisch wiederhergestellt — Popup schließen und wieder öffnen zeigt die Kartenliste innerhalb des 30-Minuten-Frischefensters ohne erneuten Scan.

4. RSS-Feed-Generierung

Audio-m4a/mp3-Dateien im Repo allein reichen Podcast-Apps nicht. Du brauchst auch docs/feed.xml (RSS). Wähle einen der zwei Modi via RSS-Feed-Modus in den Erweiterungs-Optionen.

4-1. An GitHub Actions delegieren (Standard, empfohlen)

Liegt im Repo eine Workflow-Datei (.github/workflows/build-feed.yml), baut GitHub feed.xml bei jedem Audio-Push neu und committet sie. Die Erweiterung pusht nur das Audio (leichtgewichtig), und die Workflow-Logik kannst du frei anpassen.

Standard-Vorlage: im Erweiterungs-Repo unter examples/feed-builder/ liegen vier Dateien (Workflow, Build-Skript, podcast.json, README) zum direkten Übernehmen. In dasselbe Pfadlayout im RSS-Repo kopieren (.github/workflows/, scripts/, docs/podcast.json) → Titel/Owner in docs/podcast.json anpassen → pushen. feed.xml entsteht automatisch beim ersten Audio (oder manuell via Actions-Tab → [Run workflow]).

Es werden nur Python-Standard-Library-Module genutzt, also genügt ein einziger setup-python-Step in Actions. Detail-Setup / Troubleshooting steht in der README des Beispielordners.

4-2. Erweiterung baut feed.xml bei jedem Push

Direkt nach jedem Audio-Push listet die Erweiterung das Episodes-Verzeichnis und PUTet die feed.xml. Kein Workflow-Setup, dafür zwei GitHub-PUTs (Audio + Feed) pro Karte.

Auch dieser Modus liest dieselben Metadaten wie 4-1 — wenn docs/podcast.json existiert, werden Titel/Owner/Image-Felder übernommen. Fehlt sie, wird mit Defaults (Titel = „NotebookLM Podcast", Sprache = „ko", Owner leer) gearbeitet und in der SW-Console eine Warnung ausgegeben. Für eine richtige Podcast-App-Registrierung empfiehlt sich docs/podcast.json (Format wie im Beispiel).

BASE_URL wird aus owner/name in den Erweiterungs-Optionen automatisch zu https://<owner>.github.io/<name>/ zusammengesetzt. Bei eigener Domain ist Modus 4-1 (Workflow) besser geeignet.

5. Podcast-Metadaten (Titel / Autor / Cover)

Die in Podcast-Apps angezeigten Kanal-Informationen (Titel, Beschreibung, Autor, Cover, Kategorie) liegen in docs/podcast.json in deinem Repo. Im Abschnitt „Podcast-Metadaten" der Verwaltungsseite kannst du sie per Formular bearbeiten — kein direkter JSON-Edit nötig.

5-1. Metadaten bearbeiten

  1. Beim Öffnen der Verwaltungsseite (⚙ Verwaltung) mit gespeichertem Token + Repo wird das aktuelle podcast.json automatisch geladen und ins Formular geschrieben.
  2. Titel / Beschreibung / Autor-Name · E-Mail / Sprache / Kategorie / Explizit / Cover-URL anpassen.
  3. [Metadaten speichern] klicken → docs/podcast.json im Repo wird aktualisiert → der Workflow startet und baut feed.xml mit den neuen Metadaten neu.
  4. Podcast-Apps übernehmen die neuen Daten beim nächsten Refresh (üblicherweise Minuten bis wenige Stunden).

5-2. Cover hochladen

iTunes/Apple-Podcasts-Standard — JPG/PNG mindestens 1400×1400. Manche Apps lehnen kleinere Bilder ab (das pinke „P"-Placeholder ist genau dieser Fall).

  1. In der Cover-Zeile auf Datei auswählen klicken → lokale JPG/PNG (max. 5 MB) wählen.
  2. Die Erweiterung pusht sie nach docs/cover.{jpg|png} in deinem Repo (Pages serviert sie automatisch).
  3. Das URL-Feld wird auf https://<owner>.github.io/<repo>/cover.{jpg|png} gesetzt.
  4. Erst [Metadaten speichern] sorgt dafür, dass das Feld image in podcast.json auf diese URL zeigt und der Feed sie übernimmt.
Externe Image-Hoster (z. B. Imgur, Cloudinary) funktionieren ebenfalls — sofern dauerhaft. GitHub-Pages-Hosting (Upload oben) ist am stabilsten.

5-3. Felder, die nicht im Formular liegen

retention (§7) und transcode (§8) sind nicht im Formular — selten geänderte technische Optionen, daher direkter podcast.json-Edit empfohlen. Beim [Speichern] werden diese Felder unverändert beibehalten.

6. Verwaltung gepushter Episoden

Der Abschnitt „Gepushte Episoden" der Verwaltungsseite zeigt alle Audio-Übersichten in docs/episodes/ deines Repos als Tabelle — gleiche Struktur wie die v1-Admin-Seite. Bei gespeichertem Token + Repo wird die Liste beim Öffnen automatisch geholt.

6-1. Spalten

  • Datum: YYYYMMDD-Präfix aus dem Dateinamen, im ISO-Format.
  • Notebook: Notebook-Slug aus dem Dateinamen (Bindestrich → Leerzeichen).
  • Titel: Audio-Übersichts-Titel-Slug (Hover zeigt den vollen Dateinamen).
  • Format: farbiges m4a / mp3 / mp4-Tag — große m4a sind gelb, transcodierte mp3 grün, gut auf einen Blick zu unterscheiden.
  • Größe: Bytes als MB ausgegeben.

6-2. Sortieren / Gruppieren

  • Spaltenüberschrift klicken → asc/desc umschalten. Pfeil wechselt von ▲▼ zu ▲ / ▼.
  • [Sortierung zurücksetzen (Datum ↓)] — zurück zum Default (neueste zuerst).
  • [Nach Notebook gruppieren] → Karten desselben Notebooks bündeln, Header-Zeile zeigt 📓 Notebook (N).

6-3. Bearbeiten (springt zum NotebookLM-Original)

Der [Bearbeiten ↗]-Button jeder Zeile öffnet das zugehörige NotebookLM-Notebook in einem neuen Tab. Audio-Übersichten-Titel und -Inhalt werden bei NotebookLM bearbeitet (Source of Truth) — dort korrigieren, dann hier die alte Karte [Löschen], und der nächste Sweep zieht sie mit dem neuen Titel neu.

Ist [Bearbeiten ↗] deaktiviert (grau), fehlt ein aktuelles Scan-Ergebnis zur URL-Zuordnung. Einmal [Alle Notebooks scannen] aus dem Popup heraus aktualisiert das Mapping (30 Min. gültig).

6-4. Löschen (einzeln / im Bündel)

  • [Löschen] in der Zeile — einzelner ghDelete (Bestätigungs-Dialog → 1 Aufruf → ✓).
  • Linke Checkboxen + oben [Auswahl löschen] — Mehrfachauswahl. Status-Updates während der Verarbeitung (1/N → 2/N…). Bei Teil-Fehlern OK/Fehler-Zähler.
  • Die Alle auswählen-Checkbox ganz oben togglet alle Zeilen.
  • Nach dem Löschen wird die Liste automatisch neu geladen.
Löschen entfernt nur die Datei aus dem Repo — die NotebookLM-Karte selbst bleibt. Beim nächsten Sweep zieht [Herunterladen] sie erneut (shortId-Dedup verhindert Doppel-Push). Praktisch, um falsch geholte Karten oder Karten mit Platzhalter-Titel zu bereinigen.
Geräteübergreifendes Verhalten: Löschen entfernt die Datei direkt aus dem GitHub-Repo (der gemeinsamen Source of Truth aller Geräte). Wer auf einem Gerät löscht, sieht die Karte auf jedem anderen Gerät sofort nach [↻ Aktualisieren] verschwinden — ohne chrome.storage-Sync-Verzögerung.

6-5. Skip (dauerhafter Ausschluss) und die Skip-Liste

  • [Skip] in der Zeile — löscht die Repo-Datei und trägt die shortId in die dauerhafte Skip-Liste ein. Ab dem nächsten Sweep ausgeschlossen.
  • Oben [Bulk-Skip] — Mehrfachauswahl mit Skip. Praktisch, um alte Karten zu räumen, die regelmäßig dem Retention-Cut zum Opfer fallen.
  • Toggle [Skip-Liste] klappt die Einträge auf. Pro Zeile [Aufheben], ganz unten [Alle aufheben] (die Karte wird beim nächsten Scan wieder als neu eingestuft).
[Löschen] vs. [Skip]: Löschen entfernt nur die Repo-Datei → der nächste Sweep kann dieselbe Karte erneut pushen. Skip löscht und registriert die shortId dauerhaft → auch wenn die NotebookLM-Karte noch existiert, wird sie nie wieder heruntergeladen. Damit lässt sich die Endlosschleife „alte Karte → Retention-Cut → wieder als neu erkannt → erneut geholt" verhindern.
Geräteübergreifende Synchronisation: Die Skip-Liste (skippedShortIds) liegt in chrome.storage.sync und synchronisiert sich automatisch über alle Geräte / Browser mit derselben Google-Anmeldung. Skip auf einem Gerät → der nächste Sweep auf allen anderen Geräten überspringt die Karte ebenfalls. (storage.sync-Limit ~100 KB ≈ 400 Einträge; bei Überlauf werden die ältesten verworfen.)

6-6. Feed-Reihenfolge bearbeiten

Die im RSS-Feed angezeigte Episodenreihenfolge kann frei geändert werden. Standard ist neueste zuerst nach Dateinamen-Datum, aber nach dem Speichern einer eigenen Reihenfolge werden die Episoden in der Podcast-App in dieser Reihenfolge angezeigt.

  1. Auf [Feed-Reihenfolge bearbeiten] in der Episoden-Toolbar klicken → Bearbeitungsmodus wird aktiviert.
  2. Zeilen per ☰-Handle ziehen oder ▲ / ▼-Buttons verwenden, um die Reihenfolge anzupassen.
  3. [Auf Feed anwenden] klicken → die aktuelle Reihenfolge wird als episodeOrder-Array in docs/podcast.json deines Repos gespeichert. Im Erweiterungs-direkten RSS-Modus wird feed.xml sofort neu gebaut.
  4. [Standardreihenfolge wiederherstellen] entfernt die benutzerdefinierte Reihenfolge und kehrt zu neueste-zuerst zurück.
  5. [Abbrechen] beendet den Bearbeitungsmodus ohne zu speichern.
Im Bearbeitungsmodus ist das Klicken auf Spaltenüberschriften deaktiviert (verhindert versehentliches Umsortieren vor dem Speichern). Nach dem Anwenden schließt sich der Bearbeitungsmodus automatisch und die Tabelle wird aktualisiert. Bei GitHub-Actions-RSS-Modus (4-1) löst das Speichern den Workflow aus, der den Feed neu baut.

6-7. Nach Feed-Reihenfolge anzeigen

Um die Episodenliste in der aktuell gespeicherten Feed-Reihenfolge zu sehen, den Toggle [Nach Feed-Reihenfolge anzeigen] in der Episoden-Toolbar aktivieren — ist eine benutzerdefinierte Reihenfolge gespeichert, wird diese angezeigt, andernfalls neueste zuerst. Deaktivieren kehrt zur vorherigen Sortierung zurück.

7. Aufbewahrungsrichtlinie (Rolling Window)

Um das Repo klein zu halten, ergänze ein retention-Feld in docs/podcast.json. Beide RSS-Modi (4-1 und 4-2) befolgen dieselbe Richtlinie, der Cleanup bleibt also bei einem Modus-Wechsel gleich.

{
  "title": "...",
  ...
  "retention": {
    "maxItems": 50,
    "maxAgeDays": 365
  }
}
FeldBedeutung
maxItemsNur die N neuesten Episoden behalten. Ältere Dateien werden beim Build gelöscht.
maxAgeDaysNur Episoden aus den letzten N Tagen behalten.
maxTotalMBGrößenobergrenze des Verzeichnisses docs/episodes/ (MB). Wird neueste-zuerst akkumuliert; sobald das Cap erreicht ist, wird der Rest entfernt. Soll GitHub Pages' 1-GB-Artifact-Limit umgehen. Bei ~5-MB-pro-Episode 64k-Mono-mp3 entspricht 900 MB ≈ 180 Episoden. Die neueste Episode wird immer behalten, selbst wenn sie alleine das Cap überschreitet.

Sind alle drei gesetzt, gilt UND (eine Episode muss alle Bedingungen erfüllen) — die strengste gewinnt. Wenn nur eine Bedingung gewünscht ist, andere weglassen oder auf 0 setzen. Wird das ganze retention-Feld entfernt, ist Cleanup deaktiviert (alles bleibt für immer).

Hat keinen Einfluss auf NotebookLM-Karten — nur Repo-Dateien werden bereinigt. Per Retention entfernte Episoden verschwinden aus dem RSS, aber wenn die NotebookLM-Karte noch lebt, pusht der nächste [Herunterladen] sie erneut.

8. Transcode (m4a → mp3)

NotebookLMs m4a ist 256k Stereo, ~22 MB pro Stunde. Sprachlastige Audio-Übersichten klingen auch mit 64k Mono mp3 (~5 MB) sehr gut — etwa 4× mehr Kapazität bei demselben 1-GB-Pages-Limit. Außerdem liegt die GitHub Contents API bei ~37 MiB und der Git-Data-API-Blob bei ~40 MiB — NotebookLMs 1,5–2,5 h Übersichten (40–50 MB) fallen in die Lücke, in der beide ablehnen. Transcode umgeht diese Lücke.

Zwei Modi, die parallel laufen können (was zuerst läuft, hinterlässt eine mp3, der zweite Schritt wird zum No-op).

8-1. Erweiterungsseitig (Offscreen + lamejs, automatisch)

Seit v0.4.11 transcodiert die Erweiterung m4a/mp4 selbst zu mp3, bevor sie gepusht werden. Keine Konfiguration nötig — m4a/mp4-Eingaben lösen das automatisch aus.

  • Wo: Der SW lädt das Audio und reicht den ArrayBuffer ans Offscreen-Dokument → AudioContext.decodeAudioData für PCM → lamejs-Mp3Encoder für 64k-Mono-mp3 → zurück zum SW → ghPut.
  • Geschwindigkeit: ~10 s für 30 min, ~20 s für 60 min. SW-Speicherspitze: 50 MB Eingabe + 5 MB Ausgabe.
  • Dateiname: .m4a / .mp4 wird beim Push automatisch zu .mp3.
  • Fallback bei Transcode-Fehler: Original-m4a wird unverändert gepusht — schlägt nur (selten) fehl, wenn dann das Git-Data-API-Blob-Limit greift.
Bereits im Repo liegende m4a/mp4-Dateien werden vom erweiterungsseitigen Transcode nicht erneut umgewandelt (er läuft nur im Push-Pfad). Um alte m4a/mp4 nach mp3 zu konsolidieren, aktiviere den workflow-seitigen Transcode in §8-2 — der nächste Workflow-Lauf wandelt alle m4a/mp4 in docs/episodes/ um.

8-3. Workflow-seitiges natives ffmpeg (Rückwärtskompatibilität)

Setzt das Feld transcode in docs/podcast.json, aktiviert sich der Transcode-Step des Workflows — m4a/mp4 in docs/episodes/ werden in gleichnamige mp3 umgewandelt (Original gelöscht). Native ffmpeg auf ubuntu-latest (mit libmp3lame) braucht für 1 h Audio 5–10 s. Setzt RSS-Modus 4-1 (Delegation an Actions) voraus. Praktisch, um m4a aufzuräumen, die von Builds vor v0.4.11 kommen — einmal aktivieren, der nächste Push konvertiert alles.

{
  ...
  "transcode": {
    "enabled": true,
    "bitrate": "64k",
    "mono": true
  }
}
FeldBedeutung
enabledKonvertiert nur bei true. Standard false.
bitrate"64k" / "96k" / "128k" usw. „64k" für Sprache; „96k+" wenn Musik/Sounddesign mitläuft.
monotrue mischt via -ac 1 herunter. NotebookLM-Audio-Übersichten sind ohnehin Mono, Stereo verschwendet Platz.
Workflow-Transcode + Erweiterungs-direkter RSS-Modus (4-2) gleichzeitig: Kurzzeitig erscheint ein m4a-Feed: Erweiterung pusht m4a + RSS dazu, dann läuft der Workflow (~30 s–1 min), transkodiert nach mp3 und baut RSS neu. Podcast-Apps, die in diesem Fenster aktualisieren, holen die m4a-URL. Wenn Transcode genutzt wird, RSS-Modus 4-1 (Delegation an Actions) bevorzugen, damit alles konsistent bleibt.

Erweiterungs-internes ffmpeg.wasm: nicht implementiert. Trade-offs (+25 MB Paket / 100–200 MB SW-Memory / 30 s bis Minuten Initial-Antwort) überwiegen, da der lamejs-Pfad seit v0.4.11 die meisten Fälle abdeckt. Nur relevant, falls Workflow-Setup für manche Nutzer wirklich unmöglich ist.

9. Dateinamenskonvention

YYYYMMDD__notebook-slug__shortId__title-slug.{m4a|mp3}
SegmentBedeutung
YYYYMMDDCover-Erstellungsdatum des NotebookLM-Notebooks (Datum im Cover-Bereich).
notebook-slugNotebook-Titel auf Alphanumerisch + Koreanisch reduziert und auf 40 Zeichen gekürzt.
shortIdErste 8 Hex-Zeichen der Artifact-UUID der NotebookLM-Karte. Pro Karte stabil unabhängig vom Titel, dient als Dedup-Schlüssel — erneutes Laden derselben Karte oder nachträgliches Umbenennen von Notebook / Karte in NotebookLM verursacht keinen Doppel-Push (funktioniert sogar direkt nach einem PUT, weil GET-Antworten nicht gecacht werden, also stets frisch sind).
title-slugAudio-Übersichts-Titel, identisch slugifiziert und auf 40 Zeichen gekürzt.

Das 40-Zeichen-Cap schützt Windows MAX_PATH (260) + GitHubs 255-Byte-Pfadlimit. Ein koreanisches Zeichen sind 3 UTF-8-Bytes, lange Titel können GitHubs Limit reißen; das Cap verhindert das.

Rückwärtskompatibilität: Vor v0.4.0 erstellte Dateien können im 3-Segment-Format (YYYYMMDD__notebook__title.{ext}) ohne shortId vorliegen. Beide RSS-Builder (Erweiterung + GitHub-Actions-Workflow) erkennen beide Formate, du kannst sie also lassen. Neue Pushes nutzen das 4-Segment-Format.

10. Fehlerbehebung

„Aktueller Tab ist keine NotebookLM-Notebook-Seite"

Die Erweiterung läuft nur auf NotebookLM-Notebook-Detailseiten (/notebook/<id>). Auf der Start- oder Suchseite scannt sie nicht.

„Keine Antwort — bitte Seite neu laden"

Die NotebookLM-Seite war geöffnet, bevor die Erweiterung installiert/neu geladen wurde, also ist das Content-Script nicht injiziert. Auf der Seite F5 drücken.

Push schlägt mit 401 Bad credentials oder Berechtigungsfehler fehl

  1. Auf der Verwaltungsseite [Prüfen] klicken, um die genaue Fehlerursache zu identifizieren — Token 401 / Repo 404 / fehlende Push-Berechtigung.
  2. Token 401: Token-Feld leeren und neu einfügen (auf unsichtbare trailing whitespaces achten). Hilft das nicht, ist die PAT abgelaufen — neu erzeugen (§2-2).
  3. Repo 404: Tippfehler in owner/name oder ein privates Repo, das der Token nicht sehen kann. Repository-Access-Einstellung der fine-grained PAT prüfen.
  4. Keine Push-Berechtigung: Classic-PAT braucht Scope repo; fine-grained-PAT benötigt Contents: Read and write für dieses Repo.

Dieselbe Audio-Übersicht zweimal gepusht (z. B. __audio-0.mp3, __echter-titel.mp3)

NotebookLM zeigt direkt nach Erstellung kurz Platzhalter-Titel wie audio 0, bevor sie asynchron auf den richtigen Titel umgesetzt werden. Wer im Platzhalter-Fenster lädt, landet evtl. zweimal denselben Audio. Vor dem Laden warten, bis der Titel fixiert ist. Siehe IMPLEMENTATION_NOTES.md §1.

„Chrome-Tabs-API gesperrt" oder „Tabs cannot be edited right now"

Während eines Sweeps fallen mehrere Notebooks in Folge mit derselben Meldung aus. Ursachen: tatsächlicher User-Drag, schnelle create/close-Folge, Konflikte mit Tab-Manager-Erweiterungen, Chrome-internes Rate-Limit.

Die Erweiterung wiederholt automatisch bis zu 5×, mit Backoff (500 ms → 8 s). Nach 5 Fehlern in Folge bricht der Sweep ab — die Teilergebnisse bleiben erhalten und sind via [Neue laden] nutzbar. Siehe IMPLEMENTATION_NOTES.md §5.

Workarounds: (a) erneut versuchen, ohne den Tab-Strip zu berühren, (b) andere Tab-Manager-Erweiterungen (OneTab, Tab-Grouping etc.) kurz deaktivieren, (c) etwas warten und neu starten.

Download lief, aber im GitHub ist nichts

SW-DevTools-Console prüfen:

  1. Auf chrome://extensions/ auf der Karte der Erweiterung den Link service worker klicken.
  2. In der Konsole erscheinen [push] ...-Logzeilen, die fetch / push schrittweise zeigen.
  3. Fehlermeldungen (Host, Status) zeigen, welcher Downstream-Host oder welche Berechtigung das Problem ist.

Bündel-Download erzeugt bei jeder Karte „Push-Antwort-Timeout"

Bündel-Download startet direkt nach dem Sweep, jede Karte timeoutet — die SW-Console zeigt keine [push] SW fetch host=...-Zeile. Signal: NotebookLM hat den Download-Trigger aus dem Hintergrund-Tab abgelehnt — entweder ist das Popup-Fenster nicht aufgegangen, oder das chrome.debugger-Attach ist gescheitert. Auf chrome://extensions/ die Berechtigungen (debugger / offscreen) der Erweiterung kontrollieren und die Erweiterung neu laden. Mechanik: IMPLEMENTATION_NOTES.md §9, §10.

Eine Karte schlägt mit „Datei XX MB übersteigt das GitHub-Blob-API-Limit (~40 MB)" fehl

NotebookLMs 1,5–2,5-Stunden-Übersichten erzeugen m4a-Dateien in der Lücke zwischen Contents API (~37 MiB) und Git-Data-API-Blob (~40 MiB). Der Client-Side-Transcode ab v0.4.11 umgeht das normalerweise via 64k-Mono-mp3, aber wenn dieser Transcode selbst scheitert, erscheint diese Meldung. Selten, aber wenn:

  1. Prüfen, ob der Transcode selbst defekt ist — [transcode]-Logs in SW-Console oder im Offscreen-Dokument-Console (Offscreen hat ein eigenes DevTools-Fenster).
  2. Workflow-seitigen Transcode (§8-2) als Backstop aktivieren — selbst wenn eine m4a durchrutscht, wandelt sie der nächste Workflow-Lauf um.
  3. In NotebookLM eine kürzere Audio-Übersicht erzeugen, oder Audio-Hosting umziehen (z. B. R2).

„is at X but expected Y" (HTTP 409) oder „Rule was unable to be completed" (HTTP 403)

Während ein Bündel alle 20–30 s eine Karte pusht, kann der GitHub-Actions-Workflow auto: rebuild feed parallel committen und in eine Race laufen; oder eine GitHub-Repo-Ruleset-Validierung verfehlt das 10-Sekunden-Timeout. Seit v0.4.10 wiederholt ghPut automatisch mit 1 s/2 s/4 s Backoff, daher meist unsichtbar. Erscheint 409 conflict (attempt 1/4), refreshing sha + retry im Aktivitätslog, läuft der Retry — meist nach 1–2 Versuchen erfolgreich. Schlagen alle 4 fehl, wird nur diese Karte als fehlgeschlagen markiert.

Token-Speicherort: chrome.storage.sync. Wird automatisch mit anderen Chromes geteilt, die mit demselben Google-Konto angemeldet sind und die Erweiterung installiert haben (geräteübergreifende Synchronisation). Mit aktivierter Chrome-Sync-Passphrase wird er Ende-zu-Ende-verschlüsselt — Google kann ihn nicht lesen. Ohne Passphrase wird er mit deinem Google-Kontoschlüssel verschlüsselt (gelangt also nicht an externe Server), aber Google hat technisch Zugriff. Der Token wird nur als Authorization-Header bei GitHub-API-Calls verwendet und beim Deinstallieren entfernt. Gerätespezifischer Zustand (Aufgabenfortschritt, Scan-Ergebnisse, Notebook-URL-Map) wird nicht synchronisiert und bleibt in chrome.storage.local auf dem jeweiligen Gerät.

NotebookLM-Session-Cookies: Beim Re-Fetch der Audio-Datei nutzt die Erweiterung credentials:"include", damit Cookies die Redirect-Kette (lh3.googleusercontent → ServiceLogin → lh3.google → drum.usercontent.google) durchlaufen. Die Erweiterung speichert diese Cookies nicht separat.
